Detailed Description

template<typename RealType>
struct bikappa_detail::log_accumulator< RealType >

The type in which the log-domain radius is accumulated.

log R is a stable representation of the radius, not an exact one: its absolute error is about eps |log R|, so the relative error of the radius it stands for is also about eps |log R|. Near the top of a type's range |log R| is the logarithm of the largest finite number – 88.7 in float, 709.8 in double – and the shape-boosting identity divides one of its two terms by a = kappa - 1/2, which amplifies the error of log U by 1/a: 200-fold at kappa = 0.505. In float the result is an error of a few parts in a million on a quantity whose scale is 88.7, which is larger than the gap between neighbouring floats at the overflow threshold. The radius is then not resolved finely enough to say which side of the threshold a component near it falls on, and a draw that is representable can be exponentiated one ulp high and lost. One such draw appeared in 14.2 million attempts at float kappa = 0.505: its largest component lay 3.1e-08 natural-log units – about half an ulp – below FLT_MAX, and the float log radius carried 3.5e-06 of error, a hundred times that margin.

Widening only the accumulator fixes it. The variates are still drawn in RealType, from the same engine bits, in the same order, so the sampled sequence does not change; what changes is that the sum log Y + (log U)/a and the radius built from it are formed in a type whose resolution is far finer than the margin being decided, and the value is rounded to RealType exactly once, where the component is materialized. For float that moves the resolution of log R from about 5.3e-06 to about 1.6e-14 and leaves a single rounding between the mathematics and the returned number.

For double (and for long double, where the two coincide on the platforms this header targets) the accumulator is the working type, so the arithmetic is unchanged and a double instantiation of 2.2.0 returns the same bits as 2.1.0.
