Detailed Description

Sampling primitives used to build the bi-Kappa radius.

These live here, rather than being delegated to <random>, because the radius is a Gamma ratio whose denominator shape goes to zero as kappa -> 1/2. In that limit the denominator variate underflows to exactly zero and the draw is lost, so the loader carries log X2 and never materializes X2. Taking a logarithm forces three requirements that <random> does not meet:

  • the uniform must lie in the open interval, while std::uniform_real_distribution yields [0,1) – and, in one of the two standard libraries this loader is tested against, can yield exactly 1 for float, whose logarithm is zero;
  • std::gamma_distribution uses a different algorithm in each standard library, which would make the stream, the variate count and the finite-precision failure envelope properties of the library rather than of the method; and
  • std::normal_distribution caches the second variate of each generated pair, and the two libraries return that pair in opposite orders.

Fixing all three here makes the sampled sequence a function of the engine alone.

template<typename RealType, typename GeneratorType>
log_accumulator< RealType >::type bikappa_detail::logGamma ( RealType a,
GeneratorType & gen,
RealType & ncache,
bool & ncached )

log X for X ~ Gamma(a, 1), for every a > 0, without ever forming X.

Uses the shape-boosting relation of Ahrens and Dieter (1974), X = Y U^{1/a} with Y ~ Gamma(a+1, 1) and U ~ Uniform(0,1), written additively: 

log X = log Y + (log U) / a.

The product form is what underflows: at a = 0.01, U^{1/a} = U^{100} is already zero in double for U < 7.2e-4. The sum has no such loss, because log Y is order unity and (log U)/a is a moderate negative number. The relation holds for every positive shape, so this is one code path with no domain split and no fallback, and it is rejection-free at the boosting step: exactly one Gamma and one uniform per call.

log X is a stable representation of X, not an exact one. log Y carries about one unit in the last place, and (log U)/a about one unit in the last place of |log U|/a, so the absolute error of log X grows like eps * |log X| – equivalently the relative error of the radius grows like eps * |log R|, losing roughly one decimal digit per decade of dynamic range. The uniform also has finite resolution, so |log U| cannot exceed about 36.7 (double) or 16.6 (float), and the sampled law is truncated below exp(-36.7/a). That region carries about 1.1e-16 of the probability and lies far outside the range in which any velocity component is representable.

Materialize V_j = R g_j from log R, and report whether any component overflowed.

This is the one place the loader decides what is representable, and it decides it from the value it is about to return rather than from that value's logarithm.

The obvious test – compare log|V_j| = log R + log|g_j| against log(max()) – is wrong by up to a rounding step, in both directions, and neither error is academic:

  • log(max()) is itself a rounded value and can land above the true logarithm, so exp of it need not be finite. In float, exp(log(FLT_MAX)) is exactly +inf. A draw whose log R equals log(FLT_MAX) bit for bit therefore passes a log R <= logMax test, and exp(log R) then overflows – while every component it should have produced is perfectly representable, because |g_j| < 1 pulls each of them back under the limit. One such draw occurred in 14.2 million attempts at float kappa = 0.51: log R was 0x1.62e43p+6, identical to log(FLT_MAX), the largest component's logarithm was 88.151 against a limit of 88.723, and the loader returned (-inf, +inf, +inf) – and, the overflow never having been detected, counted nothing.
  • The same rounding in the other direction makes a logarithmic test discard a draw that is representable, which is an avoidable loss.

Comparing the materialized magnitude against max() cannot have either defect: it is the number that will be returned, so the test and the result agree by construction. It is also cheaper, because the common path takes no logarithm at all – one per component is needed only where R alone overflows, which is where the log domain is doing the work anyway and where there is no accuracy left to lose.

◆ openCanonical()

template<typename RealType, typename GeneratorType>
RealType bikappa_detail::openCanonical ( GeneratorType & gen)

Uniform on the open interval (0,1), by an explicit mapping from engine bits.

b = digits - 1 random bits give an integer k uniform on [0, 2^b), and the value returned is (k + 1/2) / 2^b. Spending one bit fewer than the significand is what makes the arithmetic exact: k + 1/2 is then exactly representable and the division by a power of two is exact, so the result lies strictly inside (0,1) for every k – the smallest is 2^-(b+1), the largest 1 - 2^-(b+1). No endpoint is ever produced, so none is redrawn and none is clamped. Clamping is not a neutral choice: it replaces the end of the sampled law with an atom, which is what one standard library does for the value 1.

The bit costs one part in 2^53 (double) or 2^24 (float) of resolution, far below what log(U)/a can carry at any shape.
